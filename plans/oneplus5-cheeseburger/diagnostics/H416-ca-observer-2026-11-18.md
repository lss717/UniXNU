# H416 observation-only CoreAnimation probe

Date: 2026-11-18

## Question

H415 proved that the same boot reaches Data stage 4, launchd, SpringBoard and
`NativeLegacyDisplay`, while every recorded display counter remains zero. It
did not establish whether the missing first frame is caused by:

1. no usable `CAWindowServer` or display publication in backboardd; or
2. a running server and display with one or more `CAContext` objects, but no
   display context, root layer, renderer submission or scanout.

H416 asks only which state exists at 30, 120 and 300 seconds. It does not try
to repair the state and does not create a synthetic frame.

## Change

The A540 trace plugin in `drivers/NativeMetal/A540TracePlugin.mm`:

- reports `H416` from the bundle constructor;
- schedules only `probe_displays("observer")` and
  `probe_display_frame("observer")` at 30, 120 and 300 seconds;
- reads `CAWindowServer`, display, `CAContext`, context layer, sublayer,
  contents and renderer state;
- records the server/display/context state on every sample;
- keeps the historical diagnostic renderer compiled out under `#if 0`;
- does not call `setContext:`, `presentSurface:withOptions:`, `addSublayer:`,
  `setContents:`, `nextDrawable`, `present`, or another scene-producing path;
- does not call `MTLCreateSystemDefaultDevice`, create a `CAMetalLayer`, fill an
  IOSurface, bind a context, allocate a drawable or run the GPU self-test;
- removes the server `clientPortOfContextId:` query because it is unrelated to
  the two remaining hypotheses and could synchronize with the render server.

The plugin still loads through the existing offline-accelerator provider. That
provider is instrumentation only: it must not start the GPU, program registers,
load firmware, touch SMMU mappings or enable GPU power or ZAP.

## Decision matrix

The result is interpreted only when the H416 build marker and the accelerator
provider/userclient records come from the same boot.

| Observation | Earliest remaining explanation |
| --- | --- |
| `server=nil` or `server=0` at all three samples | CA render server was never available in the plugin's process or domain |
| server exists, `displays=0`, `ctxs=0` | display publication or CA display discovery is missing before context binding |
| server/display exist, `d0ctx=0`, `ctxs>0` | contexts exist but none is attached to display 0 |
| display context exists, `d0layer=-` or no root layer | CA selected a context without a usable root layer |
| root layer exists, but the observer-reported context tree has no content and no renderer activity | scene production or renderer setup is the next break |
| display context/root layer and renderer state exist across samples | the first blocker is at or after render submission and must be investigated through provider, `IOSurface`, IOMFB and scanout evidence |

The absence of CA selector 4, present or surface activity is not, by itself,
evidence against the accelerator: H416 intentionally suppresses all such
activity in the observer.

## Stop conditions

- If the H416 marker does not appear, the round cannot classify either state.
- If the observer itself emits selector 4, present, surface creation or context
  binding, the round is contaminated and must not be interpreted.
- If `CAWindowServer` raises an exception, the sample is unavailable; it is not
  a `server=nil` result.
- If the constructor or observer stalls the hosting process, stop the run and
  classify it as observer-induced before assigning a display root cause.
- Never add GPU power, firmware, ZAP, register-programming or scanout controls
  to recover a failed observation.

## Prior boundary

H277/H278 showed that an observation-only CA round can produce zero commits
even when a provider exists, and that 224 command buffers can be created and
released with zero binds, draws or dispatches. Those rounds identify a missing
scene as a possible later symptom. H416 is the same-boot discriminator needed
before attributing the missing frame to IOMFB, IOSurface, IOGPU or scanout.

H415's 194 `backboardd -> IOAcceleratorES` failures with `ok=0` occurred while
boot arguments explicitly disabled the accelerator. They are consistent with
that configuration and cannot be used alone to rank accelerator failure above
the missing CA display/context state.

## Static gate

`scripts/check-h416-ca-observer.py` requires the H416 marker and fixed schedule,
rejects every scene-producing selector in the active observation section,
requires the renderer to remain inside `#if 0`, and rejects the historical
persona, scene, self-test and layer schedules.

The candidate must also pass the H415 source/display/H408/H410 gates unchanged,
the 21-submodule provenance check, independent feeds and lock check, two-pass
stub/real PMGR prelink sequence, addon/trust-cache/package equality checks,
bootargs capacity, and final source-to-boot SHA verification before a device
boot.

## Device result

H416 made exactly one bounded `fastboot boot` on the unique TWRP target
`16149951`. Fastboot accepted the verified boot SHA
`493159ce2dcbb015feffc0c3205cacddb79d42312ef6d5c439d381a3aad7dbb2`.
CDC appeared as COM8 about 257 seconds after acceptance. The 360-second UXL1
capture contains 6,333 frames / 947,590 payload bytes, sequence ending at
6332, with zero CRC errors, sequence gaps, truncations or boot switches.

All three observation rounds agree:

```text
timestamp  ca probe               server state
314.98     main=1 list=6 server=6 displays=6 d0ctx=0 d0layer=- renderer=3 ctxs=2
375.18     main=1 list=6 server=6 displays=6 d0ctx=0 d0layer=- renderer=3 ctxs=2
556.38     main=1 list=6 server=6 displays=6 d0ctx=0 d0layer=- renderer=3 ctxs=2
```

The primary display is `LCD`, bounds 1080x1920. Both contexts remain
`CALayer / subs=2 / contents=0 / bounds=1080x1920`, with stable IDs
`403551756` and `2181897417`. Every round records
`bind skipped-observer-only`; there are no observer
`presentsurface`, selector-4, present, surface-creation or context-binding
markers.

The accelerator provider is no longer absent in this boot: the live log records
an `AGXAccelerator` service, three open requests, three granted user clients,
and a backboardd ABI selector-2 call. H416 therefore rejects the persistent
no-accelerator explanation as the first blocker, although full renderer
correctness is not established.

The same-boot discriminator is:

- hypothesis A, no CA server/display: excluded;
- hypothesis B, CA server/displays/contexts exist but display 0 exposes no
  context/root layer: supported.

`CADisplay` still reports `pointScale=0` and `currentMode px=0x0`, while the
display bounds and context roots are 1080x1920. `NativeLegacyDisplay` still
reports `surface=0`. These are now candidate causes or consequences at or
after display/scene publication; they are not evidence against CA server
availability.

The capture also repeats known UFS and process instability: six OCS timeouts
and recoveries, 34 stall/no-panic records, 68 UFS lock records, eight network
process traps and five `Too many corpses` messages. The hard UFS failures and
corpse storm cluster near 590-640 seconds; all three H416 CA rounds and the
sample-6000/6030/6060 display gates completed by 590 seconds. These failures
remain confounders for full-system health, but they cannot explain the
identical display/context state observed over the earlier window.

UXC1 request `424417` was sent once, ACKed at uptime 708.670805, and CDC
disappeared. Android ADB returned with `sys.boot_completed=1`, authorized
`adb reboot recovery` was issued once, and final state is TWRP
3.4.0_9-10-mauronofrio on `cheeseburger`.

Device classification:
`coreanimation-display-binding-discriminator-device-pass-no-first-frame`.
