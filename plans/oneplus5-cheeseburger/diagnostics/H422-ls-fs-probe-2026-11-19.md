# H422 LaunchServices filesystem progress probe

Date: 2026-11-19

H421 showed that `lsd` was already inside
`+[_LSInstallProgressService beginListening]` when first sampled:

```text
LSServerMain
  -> beginListening
  -> performJournalRecovery
```

A second thread waited in `restoreInactiveInstalls` at
`dispatch_group_wait_slow`, while other workers were still enumerating system
content. The H421 open-only gate was therefore below the first observed state:
it could not distinguish filesystem latency from a dispatch-group dependency.

## Unique observation

H422 keeps all H421 behavior inputs and extends only the existing low-frequency
sampler gate. The instrumented operations are:

```text
open
read
write
fsync
getxattr
```

`NATIVE_LS_GATE` reports totals, in-flight count, slow counts at 50 ms, 500 ms
and 5000 ms, maximum latency and error count. Up to eight
`NATIVE_LS_GATE_SLOT` rows retain:

```text
op, tid, vnode, active, offset, requested, residual,
duration, result, bounded attribute name, bounded open path
```

The read/write path does not resolve a full path. It records the vnode and
operation parameters so it can be correlated with an earlier open. `getxattr`
copies only its bounded attribute name. All copies target fixed storage.

The completion helpers do not print, allocate, sleep, acquire a new lock or
change an IOReturn. Text output remains in the existing `lsd` sampler.

## Device result

One bounded `fastboot boot` ran on `y9000x` with unique serial `16149951`.
The image was accepted at `2026-11-19T10:40:49.5212803+08:00`; runtime marker
was `build=H422 boot=4aa9732c`.

CDC appeared as COM3 after about 239 seconds and sustained a 480-second
capture:

```text

The first four lsd samples decisively changed the H421 interpretation:

```

All 32 slot snapshots were identical. The retained operations were three
reads and twelve `getxattr` calls. One `com.apple.decmpfs` attribute query took
143 ms; every other retained operation was 0 ms and all returned success.
There were no opens, writes, fsyncs or in-flight operations.

At `310.315550 s`, lsd pid 92 had one sampled thread, tid 553, already at:

```text
libsystem_kernel __bsdthread_terminate+0x8
  <- libsystem_pthread __pthread_terminate+0x208
```

Samples 7050, 7080 and 7110 reported pid 92 with zero sampled threads. At
`516.453596 s` lsd raised signal 10/code 0xa; it exited at `516.453708 s` with
status 0xa and was replaced through xpcproxy with fresh lsd pid 115 at
`517.068023 s`.

The first UFS OCS timeout was later, at `316.238163 s`. This establishes two
different statements:

1. A tiny read/getxattr sequence and one 143 ms decmpfs metadata lookup
   completed before any captured OCS timeout.
2. At every useful gate, lsd had no active filesystem operation. It was moving
   into termination, not sitting inside a long read or write.

H422 therefore rejects the narrow H421 follow-up hypothesis that a single
still-in-flight read/write is the direct blocker. The more specific sequence is
an early lsd lifecycle failure after compressed-file metadata access. UFS OCS
and lock starvation begin shortly afterward and become the dominant late
corpse/crash source.

## Fault profile

The window contains 55 UFS OCS timeouts, 35 `NATIVE_TRAP` records and 29
`Too many corpses` failures. The first OCS timeout follows the first useful
lsd gate by 6.511 seconds. No kernel panic or undefined-instruction panic was
observed.

## Updated ranking

1. **lsd premature termination/relaunch during LaunchServices startup.**
   Confidence high; the process has no sampled threads after its first gate
   and exits with SIGBUS at 516 seconds.
2. **`com.apple.decmpfs` / APFS named-stream metadata is the most concrete
   preceding I/O path.** Confidence medium-high. It is the only retained
   non-zero latency and is repeated by vnode.
3. **UFS lock starvation and OCS storm are a strong downstream amplifier and
   eventual terminator.** Confidence medium-high; first OCS appears after the
   first gate but before the final lsd exit.
4. **SpringBoard main-scene, renderer and display submission remain
   downstream.** No BKS reply or drawable-bearing scene was reached.

The next probe must start earlier than `native-probe-quiet=2` and record lsd
birth/exit/relaunch events together with per-vnode decmpfs getxattr/read start
and completion times. It should preserve BKS, renderer, IOMFB, IOSurface and
scanout unchanged.

## Recovery

UXC1 request `424423` was sent once and acknowledged at uptime
`877.249957 s`. Android reported boot complete; one authorized
`adb reboot recovery` returned the phone to TWRP
`3.4.0_9-10-mauronofrio`. No flash, erase, format or partition write occurred.
