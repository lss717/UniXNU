# 路线 C：Adreno 540（a5xx）GPU 内核侧 bring-up 计划

日期：2026-11-08
设备：OnePlus 5（cheeseburger / MSM8998 / Adreno 540）
目标 OS：iPad7,1 / iPadOS 17.7.11 / 21H461
状态：计划（尚未开始内核侧实现）

## 1. 目标

让 CoreAnimation/backboardd 通过一条**真实可用的 Metal 设备**渲染并出帧：

```
CA → IOAcceleratorES(AGX) → MetalPluginName → 插件 → Metal(Turnip) → 内核 GPU 驱动
   → GMU/CP/SMMU → Adreno 540 → 扫描输出
```

本计划的内核侧参考对象是 `sagit-ios-port`（小米 6 / MSM8998 / Adreno 540，同 SoC/GPU），
按其 `docs/gpu/kernel-side-bringup-plan-20261031.md` 的“内核侧上电”路线执行；只读参考，
不复制其目录布局、补丁或文件（遵守本仓库 `AGENTS.md`）。

## 1.1 C0 已完成（2026-11-08，H204–H220）

C0（投送修复）已收尾，两个验收点都达成：

1. **`addon=8/8/0/0`**：GPU addon 的 8 个文件写入 Data 卷，CRC 全部通过；
2. **插件建立真实 ABI 连接**：`NativeAdrenoMetal` 在 backboardd 里运行，
   `IOServiceOpen(0x4147)` 成功，`Query`（方法 1）与 `GetDeviceInfo`（方法 15）
   均返回成功；随后在 `BoAlloc`（方法 2）返回 `kIOReturnUnsupported`，
   那属于 C3 的缓冲区/IOVA 分配，不是投送问题。

C0 期间解决/确认的关键事实（细节见 STATUS H204–H220）：

- 21.7 MB 插件条目在旧路径下 `inflate` 失败 → 改 1 MiB 流式解压 + 分块写；
- 交接块的插件压缩流有**确定性 8 字节损坏**（addon 偏移 `0x7b9800`，
  物理 `0x186711800`，被写成 `00000000807ff000`）→ addon 增加
  "已知损坏修复表"（随包携带"错误值→原值"，内核在 CRC 校验前恢复，
  仅当当前字节完全匹配时才修）；
- boot image 上限 **81,147,904 B**（H86f 同因），payload 固定 76 MiB；
- 日志窗口会混入旧启动的 slot 与 msgbuf 残留文本 → 关键状态改写入
  `NATIVE_ACCEL_HB` 短行与心跳 `accel=`/`abi=` 字段。

## 1.2 C1 启动（2026-11-08）

本端口没有任何 RPM/SPMI/GCC 驱动，因此 C1 从**只读基线**开始，与 sagit 的
只读探测（GPU 关闭时 GPUCC 可读：`gfx3d_clk_src` 9.6 MHz、domain 1/2 关闭）
对齐：

- `sheng_gpu_power_probe()` 映射 `0x5065000`（GPUCC，0x9000）并打印非零寄存器；
- 不写任何寄存器、不读 GPU 内 RBBM（未上电时可能挂总线）；
- 下一步按 §4.2 实现 GPUCC 分支时钟 / GDSC / RPM 域投票，再读 RBBM 版本。

## 5. 架构决定

1. **内核侧上电**：按 sagit 的 P2–P4，把供电/时钟/复位/固件/ZAP/SMMU/CP 全部放在
   内核驱动里。EFI 桥只做固件/策略/内存交接，不做硬件时序（其 P1 结论：EFI 时序失败
   会停在 EFI 且无日志）。
2. **服务形态**：`QcomGPU : IOGPU : IOAcceleratorES`，发布原生 IOGPU 服务；
   user client 使用**原生 type 1**（`IOGPUDeviceUserClient`），而不是我们自建的
   `'NTNL'` 隧道。
3. **准入策略**：用 `IOUserClient::copyClientEntitlement` 校验 backboardd 的签名
   entitlement（`com.apple.backboardd` / `IOGPUDeviceUserClient` /
   `displayable-context` / `secure-mode`），替代 `NativeSandboxGrantProcess`
   与类名回退。MACF 问题因此从“属性漂移”变成“签名身份”。
4. **用户态**：优先复用我们已构建的 Turnip（`libvulkan_freedreno.dylib`）与
   metal2vulkan 桥；若与 a5xx 不一致，参考 sagit 的 `QcomMTL`/Metal 前端边界
   （只读参考，不复制）。
5. **显示**：沿用现有的 `NativeLegacyDisplay`（`IOMobileFramebufferLegacy`）；
   若 GPU 扫描输出可用，再评估 direct scanout（sagit 已验证 DPU 直扫，但我们不改
   现有显示归档，除非 GPU 链路需要）。

## 7. 先要修掉的投送问题（C0）

### 7.1 21.7 MB 可执行文件写入 EINVAL

H204 证据：安装顺序中第二个文件（插件可执行文件）返回 `EINVAL`。此前 H191/H193
曾成功安装同样大小的文件，所以嫌疑集中在“目标文件已存在 → `O_TRUNC` + `IO_UNIT`
整块写入”的路径。

诊断/修复方向（按优先级）：

1. 在 `native_gpu_addon_write` 内部按步骤打印错误（open/truncate/write/setattr/fsync），
   确认是 `vn_rdwr` 还是 `vnode_setattr`；
2. 若 `IO_UNIT` 大块写入被 APFS 拒绝：分块写入（例如 1 MiB/块，去掉 `IO_UNIT` 或按块）；
3. 若 `O_TRUNC` 路径有问题：先 `unlink` 再 `O_CREAT` 重写；
4. 若 `inflate` 失败：确认内核 zlib 对该流的行为（同一 addon 主机可完整解压）。

### 7.2 daemon 未启动（可选）

launchd 使用封印卷的 `com.apple.iomfb_fdr_loader` plist，没有使用 overlay 的同名替换。
C0 只需保证插件走 CA 路径即可；daemon 作为备用验证渠道可在 C4 后处理。

## 11. 2026-11-10 C3 收尾：结论与排除矩阵

C3 的其余部分全部通过，唯一未完成项是 **GPU 没有离开 secure 模式**。本轮把 AP 侧
所有可控机制都实测了一遍，结论如下。

### 已确认的事实

- PAS 链路真实：坏 metadata 被 TZ 拒绝（`PAS_INIT_IMAGE rc=-9`）；好镜像
  `shutdown/init/mem_setup/auth` 全部 `rc=0`；
- `PAS_MEM_SETUP` 之后 TZ 接管镜像内存（写入前读为 0，auth 后再读**挂总线**）；
- CP 的 `CP_SET_SECURE_MODE(0)`（0x66）**被执行且无错误**
  （`cpint/hwfault=0`，RPTR 正常 retire），但 `RBBM_SECVID_TRUST_CNTL` 仍为 1；
- secure 模式下：type4 寄存器写（GPMU 固件/AGC）**成功**（BABEFACE），
  经 SMMU 的**内存写全部被丢**（`CP_MEM_WRITE`、`CACHE_FLUSH_TS`，含可信窗口内）；
- AP 直写 `TRUST_CNTL` 会挂总线；读 `SECVID/TSB` 块也会挂总线。

### 已排除的假设（逐条有镜像）

| 假设 | 实验 |
| --- | --- |
| 0x66 的时机/位置 | GPMU 前/后、ME 运行/停止、kgsl/sagit/上游三种顺序 |
| ME_INIT workaround | `0x0A`（a540v1）与 `0` |
| ZAP 镜像布局/顺序 | `.mdt` metadata、`.b02@0`、`mem_setup` 前/后写入 |
| TSB 可信窗口 | 清零（上游）、`0xE8000000/0x10000000`（kgsl）、不动 |
| ZAP resume | `SCM SIP BOOT 0xA {0,13}` |
| ~~secure SMMU 配置~~ | ~~`RESTORE_SEC_CFG(GPU)`~~ **结构性无效**：OP5 的 kgsl SMMU 没有 `qcom,enable-static-cb`，厂商从不调用，`-2/-4` 不代表 TZ 裁决 |
| 可信窗口内的内存写 | `0xE9000000` 映射后仍 `mem=0` |
| 顺序 | CP 基址 ↔ ZAP ↔ ME ↔ SMMU 的所有组合 |
| GPMU 先行 | GPMU=BABEFACE → auth ZAP → 0x66，仍无效 |

### 结论

- **ZAP 已被 TZ 加载**（镜像页在 auth 后不可读），所以问题不是“PAS 假成功”或“镜像没被消费”；
- 但 `rc=0` 只证明**验签**，没有证明 ZAP 在 GPU 上**执行**；这是唯一未闭合的观测；
- `trust=1` 不是失败判据（同 SoC 的 sagit 也读到 1，靠 0x66 清零；reset 判据是
  `TrustControl > 1`，提交判据才是 `== 0`）；
- device id 语义已确定（`GPU=18`、`UFS=19`），H236dv 在 19 挂死是给工作中的 UFS 做
  secure 配置——**永远不要重跑**；
- `RESTORE_SEC_CFG` 一行已作废（见上表）：原厂路径根本不发这个调用。

### 后续实测（H236dy–eg，见 build-environment §23–§26）

- **P2**：auth 前后 CP/RBBM 快照一字不差（ME 运行/停机两种状态）→ `AUTH_AND_RESET`
  不复位 AP 可见的 GPU 状态；
- **P1**：auth 之后**立刻**读 `TRUST_CNTL` 就是 1（中间只有一个 GPMU 寄存器读）→
  TZ 在 auth 时没有清过它；
- **V1**（PAS 先、reset 后）未充分测试：PAS 跑在时钟打开之前，读数为 `ffffffff`；
- **TZ/hyp 日志**：hyp 日志明文可读但与 Android 逐字相同、无 GPU/PAS 记录；qsee 环形
  缓冲加密；整段遍历 `0x146BF720` 会挂总线；
- **hw-init 全量复刻**（VBIF/CP_PROTECT/TSB/ME_INIT/LM/SP-TP collapse/GPMU + a540 hwcg
  95 条）后结果不变；
- **与 Android 逐项 A/B**：`pas-id=13`、`a540_zap`、`b00`、**`b02` 逐字节相同**，mdt 仅
  签名块不同（`b01` 是 `PT_NULL` 的 HASH 段，从不装载），启动路径同为纯 SCM。

**最终结论**：AP 侧输入与 hw-init 已与同机可工作的 Android 路径完全对齐，secure 位仍不动；
剩余差异只在安全世界内部。C3 冻结在 H236eg（kernel `ca13c26c…`、boot `26f0c53f…`）。
C4/C5 代码准备可并行，但在 secure 位解决前不要上机提交真实 GPU 作业。
