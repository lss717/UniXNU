# H419 BKS reply and main-scene boundary

Date: 2026-11-18

## Question

H418 closed the AppleKeyStore gate and showed that the `0x5b9173` BKS
main-screen request left launchd's queue between samples 6000 and 6030. It did
not retain the exact queue, direct-delivery, receive and reply events. H418 also
showed two display-bound `CAContext` objects whose bounded layer trees had no
contents, but it sampled only their ids and root fields.

H419 asks four ordered questions:

1. Does the exact BKS request reach launchd, get delivered/received, and receive
   a reply from a known peer?
2. Does the display-bound context set change after the reply?
3. Does any bounded layer become contents-bearing?
4. Does a drawable, draw, commit, IOMFB selector 4, IOSurface transfer or
   presented frame appear after either event?

## Changes

The candidate remains observation-only.

The H413 IPC recorder gains a dedicated 512-entry ring for SpringBoard and
launchd traffic. It is independent from the existing 1,024-entry ring.
The H419 ring records:

- send (`S`);
- enqueue (`Q`);
- direct delivery (`D`);
- receive/select (`R`);
- message id, bits and size;
- sender/receiver pid;
- queue, remote and local reply port objects;
- receiver thread id and the state supplied by the IPC hook.

The ring captures all SpringBoard/launchd traffic, the observed `0x5b9173`
message id, and events matching the request/reply ports learned from the
SpringBoard stack. The IPC path performs fixed-size integer copies only. It
does not print, allocate, sleep or take a new lock.

The A540Trace utility-queue observer changes its build marker to `H419` and:

- retains an eight-entry per-boot context table;
- reports the first fixed sample at which each context id is present;
- queries `contextIdHostingContextId:`, `clientPortOfContextId:` and
  `taskNamePortOfContextId:` once for a new context;
- records root object identity, root sublayer count, total bounded nodes and
  the number of nodes with non-nil contents;
- emits only new or changed context states.

The active path still does not call `setContext:`, `setLayer:`, `addSublayer:`,
`setContents:`, `presentSurface:withOptions:`, `nextDrawable` or `present`.
The retired synthetic renderer remains compiled out.

## Decision table

| Exact observation | Earliest remaining boundary |
| --- | --- |
| no `S/Q/D/R` for `0x5b9173` | request path or recorder discovery |
| `Q` without `D/R` | launchd scheduling or queue delivery |
| launchd `R` without launchd-to-SpringBoard `S` | reply construction/send |
| reply `S` but SpringBoard does not reselect/complete | send-once delivery or BKS receive |
| BKS reply and later context update | inspect the updated layer/content fields |
| context state stable and no contents after reply | main-scene content production |
| contents-bearing layer but no drawable/commit | renderer/scene interaction |
| drawable/commit but no selector 4 | display/surface handoff |
| selector 4 but no validation/copy/transfer | IOSurface or IOMFB parser |
| transfer but no panel frame | MSM8998 scanout |

An unchanged context after the reply is evidence for a later scene/content
boundary. It is not evidence to modify IOMFB, IOSurface or scanout, which remain
conditional on selector 4.

### BKS request and response

The dedicated ring had 92 entries and zero loss when sample 6000 ran. The
SpringBoard request record is:

```text
serial 85  S  id=0x5b9173 size=32 from=27 to=1
serial 86  Q  id=0x5b9173 size=32 from=27 to=1
```

At sample 6000, launchd still had this request queued (`q=1`, reply count 0).
The later records show the complete delivery path:

```text
serial 109  R  id=0x5b9173 receiver=56/backboardd thread=618
serial 110  S  id=0x5b91d7 size=68 from=56/backboardd to=27/SpringBoard
serial 111  D  id=0x5b91d7 size=68 receiver=293/SpringBoard
```

The response destination is the exact local reply port from the SpringBoard
request. The response id differs from the request id, explaining why a
same-id-only search missed it in H418. A second client, chronod pid 89, also
sent `0x5b9173`; it does not affect the SpringBoard-to-backboardd correlation.

The records were emitted retrospectively at sample 8010. H419 stored event
order and ports but not an event timestamp, so the live print time is not the
message time. H420 should add an event tick while retaining the independent
ring.

Conclusion: the BKS main-screen request is delivered and receives a reply from
backboardd. A permanent queue or missing reply is no longer a first-frame root
cause.

### CA context and renderer

At 419.416 seconds the observer saw one display-bound context
`0x5d9ae0de`. At 423.676 seconds it saw two:

```text
0x5d9ae0de displayId=0x1 mask=0xffffffff bounds=1080x1920 rootContents=nil
0xc6aa2b12 displayId=0x1 mask=0xffffffff bounds=1080x1920 rootContents=nil
```

The bounded walk covered eight nodes and none had contents. The type-1
accelerator client and ABI selector 2 were present. There were zero
`nextDrawable`, draw, command-buffer commit, `presentSurface:withOptions:`,
legacy validation, transfer or frame records in the capture.

The new context-change observation did not run correctly. Both rounds emitted
`NATIVE_MTL srv ctxfull observer` because the index fix-up compared `index`
against a reassigned `free_index` rather than the table length. Consequently,
client/task-name ports and add/change records are unavailable. The existing
server state and bounded layer dumps remain valid.

### Confounders and recovery

The complete capture contains two UFS OCS timeouts and two retries/recoveries,
the first at 688.368 seconds. Both context rounds and the BKS transaction are
earlier. There was no kernel panic or undefined instruction. Two mediaserverd
instances exited with signal 6 at 362.160 and 456.757 seconds, before the UFS
window.

UXC1 request `424420` was sent once, ACKed at uptime `744.690403`, and CDC
disappeared. The automation did not send `adb reboot recovery`; the user
reported entering TWRP manually after the Android wait. TWRP
`3.4.0_9-10-mauronofrio` was verified on the unique serial afterward.

Classification:
`bks-reply-complete-main-scene-content-empty-context-change-observer-bug`.
It does not claim a first frame. It moves the actionable boundary to
main-scene completion/content production and requires H420 to repair the
context-table index and avoid focusing the BKS ring on non-SpringBoard samples.
